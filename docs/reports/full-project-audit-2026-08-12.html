Section 01 — Not previously reported

Three defects the audit chain could not see

Every agent audited the repository. The first two appear only when you query the live project — both caused by work applied to production out-of-band, outside the migration and deploy tooling. The third is the mirror image: code that is correct in isolation but never connected, invisible to any check that reads one layer at a time.

P0-A · The deleted Onfido function is still deployed and still writes gender_verified

PR #29 deleted supabase/functions/verify-with-onfido/ from the repo, and the migration plan, the grep gate, and the database agent all recorded Onfido as fully removed. Deleting the directory does not undeploy the function. It is live right now:

slug: verify-with-onfido   status: ACTIVE   version: 3   verify_jwt: true
id:   7a08d2b5-1696-4894-958c-887ec223d38c

Its own source — recovered from 031c1e7^ — carries the hole the Shufti migration was written to eliminate. Line 315 concedes it, line 366 acts on it:

315:  // Verify webhook signature (simplified - in production, use proper signature verification)
319:  if (!signature || !webhookSecret) {          // presence check only — never validated
366:            gender_verified: true,             // the women-only admission flag

The webhook branch is entered on the mere presence of an x-onfido-signature header, and the signature is never verified against the payload. gender_verified is the flag is_verified_female() reads and the women_only_requires_verified_female constraint enforces. Exploitability depends on whether ONFIDO_WEBHOOK_SECRET is still set in prod secrets — if it is unset the branch errors out early. That distinction is not worth relying on. The function has no callers, no purpose, and a known auth bypass on the platform's most safety-sensitive flag.

Fix: supabase functions delete verify-with-onfido, then confirm no ONFIDO_* secrets remain.

P0-B · The Shufti schema is live but absent from the migration ledger — the next db push will fail

Step 5 of the migration plan applied the Shufti DDL through the Management API /database/query endpoint, because db push needed a DB password that wasn't available. The DDL landed. The ledger entry did not:

shufti_migrations_in_ledger : 0          ← expected 2
latest_ledger_version       : 20260717180000
onfido_cols_remaining       : 0          ← DDL *is* live
provider_col_live           : 1
provider_check_def          : CHECK (provider = ANY (ARRAY['shuftipro','onfido',
                                      'stripe_identity','persona','veriff']))

So the database is correct and the ledger is a liar. The next supabase db push will replay 20260812000000_shufti_rebrand.sql, hit RENAME COLUMN onfido_check_id TO provider_reference against a column that no longer exists, and abort — taking every later migration with it. This is a live tripwire under the very next backend deploy either repo attempts.

Fix: supabase migration repair --status applied 20260812000000 20260812010000, then supabase db diff --linked to confirm the ledger and schema agree before pushing anything.

P0-C · The verification UI cannot reach the Shufti code — no user can verify

Found while inventorying user-facing screens after the audit. The Shufti pipeline is real, deployed, and proven end-to-end against prod — and completely unreachable from the app. Both verification entry points call repository methods that PR #29 left as UnimplementedError:

photo_capture_screen.dart:316 → submitPhotoVerification() → throw UnimplementedError
id_upload_screen.dart:296     → submitIdVerification()    → throw UnimplementedError

The working methods — submitShuftiVerification / pollShuftiVerification — were added to the implementation only, never to the VerificationRepository interface, and have zero callers in the presentation layer. Before PR #29 the button hit a simulation stub that always approved after two seconds; now it throws. That is a user-facing regression, and it makes the remaining DoD item — a live test with a real female volunteer's ID — impossible to perform through the app.

Two further defects surfaced in the same screens. photo_capture_screen.dart navigated to the result page on photo capture rather than on submission, always reporting success: true; id_upload_screen.dart did the same on any settled state, including failure. Both would have shown users a success screen for a verification that never happened.

Underneath the wiring sits a design gap: Shufti Mode C requires the document and the selfie in one submission, but the two screens were built as terminal alternatives, each submitting alone. A document without a face match proves the document is genuine, not that it belongs to the person holding it — which is precisely the binding the women-only gate depends on.

Fix: branch fix/verification-ui-wiring — the document step now stages its capture, the selfie step submits both together, and navigation reports the real outcome. Adds a selfie to the ID flow, so it is a deliberate product change requiring sign-off. 9 new tests, 46/46 green, flutter analyze clean.

Undocumented invariant: what does gender_verified actually mean?

Women-only mode is gated by two separate checks in matching_repository_impl.dart:815–932 — isVerifiedForWomenOnly() reading gender_verified, and getUserGender() == 'female'. The edge function sets gender_verified = true for any approved gender, male included. So the flag means "gender was verified", not "verified female" — and only the conjunction is safe. This is load-bearing safety logic held together by an undocumented convention, with in-memory state (_womenOnlyModeEnabled) that can silently diverge from the database because the write failures are caught and ignored. Document the invariant, then extract to the safety layer per Story H.3.

Section 08 — Verdict

Engineering quality is good. Deployment discipline is the actual risk.

Both codebases show real care: RLS-first schema design, no service-role key anywhere in a client, an honest signature-keyed test gate, pgTAP proofs on the safety-critical policies, and a documentation set that stays consistent across two repos. The Shufti migration in particular was executed well — proven signature algorithm, tampered-payload rejection, vendor-neutral schema.

The risk is not in the code. It is that production has been modified through side channels — a function deleted from the repo but not from the platform, a schema applied through a query endpoint but not recorded in the ledger. Both P0s are invisible to every repo-based check the project runs, including its own CI, its grep gates, and five of six audit agents. That is the class of defect worth building a guard against: a deploy-time reconciliation check that diffs live functions and live ledger against the repo.

Launch readiness: not today, but closer than the agent reports suggested. Steps 1–2 are hours of work and clear the live defects. Phase 0 completion plus a release checklist is the remaining gate — realistically one sprint, not the two-plus that the stale drift narrative implied.
